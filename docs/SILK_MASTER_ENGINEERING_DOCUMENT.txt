1. EXECUTIVE SUMMARY & DESIGN PHILOSOPHY
-------------------------------------------------------------------------------
SILK is a vertical arena action game built around dynamic movement. The architecture
is founded on a lightweight, data-oriented Entity-Component-System (ECS), strict
unidirectional data flow, and zero-allocation rendering pipelines. 

Core Pillars:
- Data-Oriented ECS: Pure data components (e.g., TransformComponent, TetherComponent) 
  decoupled from logic. Entities are represented by numeric IDs (EntityId) for O(1) 
  lookups and zero garbage collection pressure.
- Unidirectional Command/Event Bus: Gameplay systems issue imperative Commands 
  (downward to physics), while Simulation/Physics systems emit past-tense Events 
  (upward to view/audio/UI).
- Zero-Allocation Rendering: High-refresh-rate (144Hz+) stability is guaranteed by 
  utilizing class-level scratchpad vectors and quaternions, entirely eliminating 
  per-frame memory allocations in the render loop.
- Deterministic Pipeline: Time and scheduling are abstracted via IClock and IScheduler 
  interfaces, enabling headless, fixed-step simulation testing.
- First-Class Observability: Integrated Profiler, Event Traffic Tracker, and toggleable 
  Debug Wireframe/Telemetry overlays ensure long-term maintainability.

2. THE NERVOUS SYSTEM: FRAME EXECUTION PIPELINE
-------------------------------------------------------------------------------
The GameLoop enforces a strict, dual-layer sequential pipeline separating the fixed
timestep update thread (dt = 1/60s) from the variable-rate render loop.

A. FIXED-TIMESTEP UPDATE (60Hz Ticks)
1. Input Phase: PlayerInputSystem polls DOM/Keyboard, writing to InputIntentComponent.
2. Intent & AI Phase: 
   - PlayerMovementSystem reads intents and stats, dispatching Commands (e.g., 
     SetKinematicVelocityCommand) to the CommandBus.
   - WardenBrainSystem evaluates AIContext, transitions states, and dispatches Commands.
3. Command Resolution Phase: RapierWorldSystem (Adapter) synchronously processes the 
   CommandBus, mutating ECS Velocity and Target components.
4. Simulation Phase:
   - PlayerKinematicsSystem applies pendulum-tension constraints to Target components.
   - EnvironmentCollisionSystem resolves AABB platform and border collisions.
5. Physics Phase: RapierWorldSystem steps the WASM simulation, syncing Rapier bodies 
   to ECS TransformComponents, and publishes Events (e.g., ROPE_TENSION_CHANGE).

B. VARIABLE-RATE RENDERING PASS (Variable FPS)
1. Render-Sync Phase: TransformSyncSystem interpolates previous and current 
   TransformComponents to Babylon nodes using zero-allocation scratchpad math.
2. Presentation Phase: RopeVisualizerSystem regenerates dynamic line ribbons using 
   pre-allocated Vector3 arrays to simulate rope sag.
3. Camera Phase: CameraSystem applies spring-mass-damper tracking and screen shake 
   using scratchpad vectors.
4. Render Phase: RenderSystem draws the active Babylon WebGL call.
5. Audio/UI Phase: Event-driven systems mutate Tone.js synthesizers and DOM nodes.
6. Diagnostics Phase: Profiler records system timings; DebugTelemetryOverlay renders.

3. ARCHITECTURAL PATTERNS & SOLID COMPLIANCE
-------------------------------------------------------------------------------
- Single Responsibility Principle (SRP): Systems contain only execution logic. 
  Physics math, collision resolution, and WASM stepping are isolated in separate systems.
- Open/Closed Principle (OCP): Warden AI utilizes a formal State Pattern operating on 
  an AIContext. Adding new behaviors requires only new state files and components.
- Liskov Substitution Principle (LSP): SystemManager expects general ISystem structures.
- Interface Segregation Principle (ISP): Physics exposes IReadablePhysics. Visuals 
  expose IVisualRegistry. Systems only depend on the exact data slices they require.
- Dependency Inversion Principle (DIP): Systems depend on ComponentStores and EntityRefs, 
  completely decoupled from concrete rendering or physics engine implementations.
- Composition over Inheritance: Entities are composed of pure data components rather 
  than inheriting from monolithic base classes.

4. DATA-ORIENTED ECS & SUBSYSTEM BREAKDOWN
-------------------------------------------------------------------------------
- EntityRegistry: Manages numeric EntityId lifecycles.
- ComponentStore<T>: Type-safe, contiguous storage for pure data structures.
- EntityRefs: Dependency injection context for core entity IDs (player, warden, anchor).
- CommandBus: Synchronous, typed dispatcher for downward imperative actions.
- EventBroker: Asynchronous, typed pub/sub for upward state notifications.

Key Subsystems:
- RapierWorldSystem: Pure WASM adapter and Command handler. Contains zero gameplay math.
- PlayerKinematicsSystem: Custom pendulum and tether constraint solver.
- EnvironmentCollisionSystem: AABB resolution using shared EnvironmentColliders data.
- EntitySpawnerSystem: Authoritative factory for entity creation and visual mapping.

5. OBSERVABILITY, TOOLING & DETERMINISM
-------------------------------------------------------------------------------
- Profiler: Tracks exact execution timings per system and overall FPS/Frame Time.
- DebugWireframeSystem: Toggleable (F3 / Backtick) rendering of AABB colliders, 
  tether constraints, and anchor points.
- DebugTelemetryOverlay: DOM-based overlay displaying real-time system timings, 
  entity counts, and event bus traffic.
- IClock & IScheduler: Abstractions allowing the GameLoop to run independently of 
  requestAnimationFrame for automated testing and server-side authority.
