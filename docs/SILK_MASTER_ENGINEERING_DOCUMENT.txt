1. EXECUTIVE SUMMARY & DESIGN PHILOSOPHY
-------------------------------------------------------------------------------
SILK is a vertical arena action game built around dynamic movement. The architecture
is founded on a lightweight, data-oriented Entity-Component-System (ECS), strict
unidirectional data flow, phased system orchestration, and zero-allocation rendering.

Core Pillars:
- Phased System Orchestration: Systems are ordered deterministically by designated 
  SystemPhase layers rather than registration sequence, eliminating single-frame lags 
  and initialization races.
- Data-Oriented ECS: Pure data components decoupled from logic. Dynamic aspect queries 
  and tag component stores (PlayerTag, WardenTag, AnchorTag) replace rigid hardcoded 
  entity reference lookups.
- Deferred Command Buffering: Systems issue commands to a buffered queue. Commands are 
  deferred and flushed atomically at the entry boundary of the physics step, ensuring 
  unidirectional state mutations and preventing frame-loop side effects.
- Zero-Allocation Rendering: High-refresh-rate stability is guaranteed by 
  utilizing class-level scratchpad vectors, quaternions, and optional lifecycle hooks 
  (e.g., rendering-only systems have no update stubs), eliminating garbage collection pressure.
- Out-of-the-Box Compilation: Employs rapier3d-compat to integrate the WebAssembly 
  physics engine directly into standard ESM bundles, bypassing complex bundler loaders.


2. THE NERVOUS SYSTEM: FRAME EXECUTION PIPELINE
-------------------------------------------------------------------------------
The GameLoop enforces a strict, phase-sorted pipeline separating gameplay updates 
from presentation render cycles. Systems are registered to specific SystemPhase 
layers and sorted during engine bootstrap.

A. SYSTEMPHASE PIPELINE LAYERS
1. Phase 0: SystemPhase.Input
   - PlayerInputSystem: Polls keyboard/mouse inputs, writing directly to the 
     InputIntentComponent of active player-tagged entities.
2. Phase 1: SystemPhase.Intents
   - PlayerMovementSystem: Evaluates inputs, dispatching SetKinematicVelocity and 
     SetRopeMaxLength commands to the CommandBus.
   - WardenBrainSystem: Drives Warden finite state machine actions and transitions, 
     dispatching movement commands based on sensory states.
3. Phase 2: SystemPhase.Kinematics
   - PlayerKinematicsSystem: Applies gravity, swing mechanics, and tether length 
     constraints, updating kinematic targets.
4. Phase 3: SystemPhase.Collision
   - EnvironmentCollisionSystem: Adjusts movement targets based on platform AABB 
     overlapping to resolve environment collisions prior to physics stepping.
5. Phase 4: SystemPhase.PhysicsStep
   - RapierWorldSystem: First flushes all deferred commands from the CommandBus. 
     Next, updates Rapier kinematic body translations to match kinematic targets, 
     steps the C++ WASM physics simulation, and synchronizes resulting body transforms 
     back to ECS TransformComponents.
6. Phase 5: SystemPhase.RenderSync
   - TransformSyncSystem: Interpolates prev/curr TransformComponents using alpha ratios 
     and slerp calculations to update visual Babylon nodes.
   - RopeVisualizerSystem: Regenerates procedural rope sag ribbons based on player 
     and anchor transforms.
   - CameraSystem: Tracks players and applies spring-mass-damper smoothing with camera shake.
   - Audio/UI Systems: Direct Tone.js FM synthesis and DOM HUD updates.


3. ARCHITECTURAL PATTERNS & SOLID COMPLIANCE
-------------------------------------------------------------------------------
- Single Responsibility Principle (SRP): Systems hold pure execution logic. Physics 
  stepping, collision math, and input capturing are kept strictly isolated.
- Interface Segregation Principle (ISP): The ISystem contract features optional 
  update, render, and initialization lifecycles. Rendering-only systems (such as 
  RopeVisualizerSystem) do not require empty update stubs.
- Open/Closed Principle (OCP): State AI utilizes modular Warden states that read and 
  evaluate contextual components. New behaviors can be introduced with zero changes 
  to the central brain system.
- Liskov Substitution Principle (LSP): SystemManager handles general systems, sorting 
  and stepping execution sequences based on their phase properties.
- Dependency Inversion Principle (DIP): Gameplay systems write to decoupled CommandBus 
  and ComponentStores, completely isolated from direct physics or WebGL rendering drivers.


4. DATA-ORIENTED ECS & SUBSYSTEM BREAKDOWN
-------------------------------------------------------------------------------
- EntityRefs: Backed by dynamic tag ComponentStore lookups (PlayerTag, WardenTag, AnchorTag). 
  Resolves entity IDs dynamically at runtime, allowing fallback assignments for backwards 
  compatibility while keeping the design open to multiple enemies or players.
- CommandBus: Buffered queue that collects imperative actions. By deferring command execution 
  to a dedicated flush boundary in the physics step, frame loop race conditions are avoided.
- EventBroker: Synchronous event dispatcher used for upward UI alerts, camera shakes, 
  lighting transitions, and acoustic updates.


5. OBSERVABILITY, TOOLING & DETERMINISM
-------------------------------------------------------------------------------
- Profiler: Tracks timing latency per phase and records rendering frame rates.
- DebugWireframeSystem: Renders visual wireframes of collision boxes and constraints, 
  implementing the RenderSync phase.
- DebugTelemetryOverlay: Direct diagnostic overlay displaying system profiling metrics and 
  active entity states.
- Void-Eval Safety: Unused fields in skeletal diagnostic classes are evaluated with standard 
  TS "void" operators, satisfying compiler checks while maintaining zero-overhead declarations.

7. DEVELOPMENT WORKFLOW & TESTING
-------------------------------------------------------------------------------
- Standard physical updates run at a fixed 60Hz step. Ensure all visual interpolation 
  code uses pre-allocated scratchpad arrays to prevent garbage collection spikes.
- Always run "npm run build" to verify type safety across all system files prior to deployment.
- Diagnostic systems should declare all structural references, using standard "void" reads 
  to satisfy compiler checks without adding operational complexity.
