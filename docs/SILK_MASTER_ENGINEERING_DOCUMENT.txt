PURPOSE
-------------------------------------------------------------------------------
This document is the authoritative engineering and architectural blueprint for
SILK. It is designed as a complete AI handoff package for future build sessions.

This is NOT a lightweight game jam architecture.
This is a production-minded vertical slice framework optimized for:
- maintainability
- iteration speed
- modularity
- deterministic gameplay systems
- extensibility
- debugging clarity
- future scalability

The design philosophy intentionally avoids:
- god objects
- giant manager classes
- hidden mutable state
- monolithic gameplay files
- brittle inheritance chains
- tightly coupled gameplay logic
- architecture that collapses under feature expansion

The system is intentionally designed around:
- composition over inheritance
- event-oriented communication
- explicit ownership boundaries
- feature encapsulation
- deterministic fixed-step simulation
- dependency inversion
- observable runtime systems
- isolated feature modules
- testable subsystems
- low-risk refactors

SILK boots directly into gameplay.
There is:
- NO title screen
- NO settings menu
- NO save/load
- NO multiplayer
- NO profile management
- NO account systems
- NO network abstraction

The game starts in the arena immediately.

===============================================================================
HIGH LEVEL GAME SUMMARY
===============================================================================

SILK is a vertical arena predator-prey combat game focused on:
- momentum
- tension
- elastic traversal
- wall slide charging
- silk rope physics
- psychological boss AI pressure
- environmental control

Core loop:
1. Player wall-slides to build slide charge (visually glowing emissive color)
2. Player launches using silk momentum, with jump velocities scaling by charge
3. Dynamic anchors hook dynamically to platform undersides or ceilings
4. Warden AI responds dynamically with emotional state and light-pulse shifts
5. Player lands strikes during Warden recovery or Frenzied state windows
6. Boss battle intensifies with a Fake-Death phase and Berserk Overdrive rage

Movement quality is the focal priority of the experience.

===============================================================================
CORE ENGINEERING PHILOSOPHY
===============================================================================

1. SYSTEMS OWN THEIR DATA
-------------------------------------------------------------------------------
Avoid shared mutable state whenever possible.

Every major subsystem owns:
- its lifecycle
- its update path
- its runtime data
- its configuration
- its teardown logic

Other systems communicate through:
- events
- readonly interfaces
- explicit contracts

2. COMPOSITION OVER INHERITANCE
-------------------------------------------------------------------------------
Do NOT build deep entity inheritance trees.

3. NO GLOBAL MANAGER SPRAWL
-------------------------------------------------------------------------------
Use narrow orchestration layers and isolated systems.

4. EVENT-ORIENTED COMMUNICATION
-------------------------------------------------------------------------------
Systems communicate via a strongly typed EventBroker.

5. DETERMINISTIC GAMEPLAY
-------------------------------------------------------------------------------
Core gameplay simulation runs at a fixed 60Hz step. Rendering interpolates.

6. OBSERVABILITY FIRST
-------------------------------------------------------------------------------
Every major runtime system must expose:
- debug metrics
- runtime status
- profiling hooks
- validation helpers

The engine should be inspectable while running.

===============================================================================
ABSOLUTE ARCHITECTURAL RULES
===============================================================================

RULE 1: Gameplay systems NEVER directly touch React state.
RULE 2: Babylon scene objects NEVER become source-of-truth gameplay state.
RULE 3: React is presentation only.
RULE 4: Physics/Kinematics owns authoritative movement truth.
RULE 5: Visuals read gameplay state. Gameplay never reads visuals.
RULE 6: Every system has: init(), update(), dispose().
RULE 7: No runtime circular dependencies.
RULE 8: All cross-system communication must be explicit.
RULE 9: Every feature module must be removable without catastrophic rewrites.
RULE 10: No hidden side effects inside getters/setters.

===============================================================================
STATE MANAGEMENT STRATEGY
===============================================================================

Zustand is NOT the simulation engine. Zustand manages only HUD overlay triggers,
debug toggles, and readonly snapshots. Simulation state remains fully encapsulated
inside ECS systems and dynamic ComponentStores.

===============================================================================
GAME LOOP ARCHITECTURE
===============================================================================

Simulation: 60Hz fixed timestep.
Rendering: Uncapped with alpha interpolation.

Pipeline:
Input -> Fixed Simulation -> Physics -> Gameplay Systems -> Events -> Render Sync -> Babylon Render

===============================================================================
REFINED PLAY AREA & ALIGNMENT SPECIFICATIONS
===============================================================================

Logical limits must align perfectly to prevent collision sticking and clipping:
- Playable Area limits: Left/Right X: [-15.0, 15.0], Floor/Ceiling Y: [0.0, 28.0]
- Left Wall Visual center: -16, width 2 (spans -17 to -15)
- Right Wall Visual center: 16, width 2 (spans 15 to 17)
- Player mesh: Capsule radius 0.4, height 1.8 (clamping coordinates playerHalfW = 0.4, playerHalfH = 0.9)
- Warden mesh: Sphere radius 1.0 (clamping coordinates wHalfW = 1.0, wHalfH = 1.0)

===============================================================================
ROPE SYSTEM & DYNAMIC GRAPPLING
===============================================================================

Dynamic overhead grapples target the ceiling (Y = 28) or the undersides of Left
and Right platforms depending on the player's lateral coordinate:
- Left Platform underside: Y = 11.5 (spans X: [-15, -7])
- Right Platform underside: Y = 17.5 (spans X: [7, 15])

Tension synthesizer scales audio pitch based on tension, escalating to high-frequency
screeches when the Warden enters BERSERK OVERDRIVE and dropping to eerie lows on DEFEATED?.

===============================================================================
WARDEN AI BEHAVIOR PHASES
===============================================================================

State cycle:
1. PHASE 1: DORMANT -> HUNTING -> CHARGE_PREP -> CHARGE_ATTACK -> RECOVERY
2. FAKE DEATH: Hit 0% HP -> enters FAKE_DEATH (dazed, light turns off, low pitch audio drone)
3. PHASE 2 (BERSERK OVERDRIVE): Revives with 50% HP, bright orange glow, relentless pursuit speed, screeching synth drone escalation. Permanently dies on next 0% HP.
