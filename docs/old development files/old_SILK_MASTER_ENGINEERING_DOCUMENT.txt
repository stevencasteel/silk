PURPOSE
-------------------------------------------------------------------------------
This document is the authoritative engineering and architectural blueprint for
SILK. It is designed as a complete AI handoff package for future build sessions.

This is NOT a lightweight game jam architecture.
This is a production-minded vertical slice framework optimized for:
- maintainability
- iteration speed
- modularity
- deterministic gameplay systems
- extensibility
- debugging clarity
- future scalability

The design philosophy intentionally avoids:
- god objects
- giant manager classes
- hidden mutable state
- monolithic gameplay files
- brittle inheritance chains
- tightly coupled gameplay logic
- architecture that collapses under feature expansion

The system is intentionally designed around:
- composition over inheritance
- event-oriented communication
- explicit ownership boundaries
- feature encapsulation
- deterministic fixed-step simulation
- dependency inversion
- observable runtime systems
- isolated feature modules
- testable subsystems
- low-risk refactors

SILK boots directly into gameplay.
There is:
- NO title screen
- NO settings menu
- NO save/load
- NO multiplayer
- NO profile management
- NO account systems
- NO network abstraction

The game starts in the arena immediately.

===============================================================================
HIGH LEVEL GAME SUMMARY
===============================================================================

SILK is a vertical arena predator-prey combat game focused on:
- momentum
- tension
- elastic traversal
- wall slide charging
- silk rope physics
- psychological boss AI pressure
- environmental control

Core loop:
1. Player wall-slides to build tension
2. Player launches using silk momentum
3. Anchors manipulate arena traversal
4. Warden AI responds dynamically
5. Player lands strikes
6. Combat escalates through emotional states

The entire game hinges on:
- movement feel
- readable momentum
- audiovisual tension feedback
- precision simulation
- responsiveness

Movement quality is more important than:
- content volume
- graphical fidelity
- feature count

===============================================================================
CORE ENGINEERING PHILOSOPHY
===============================================================================

1. SYSTEMS OWN THEIR DATA
-------------------------------------------------------------------------------
Avoid shared mutable state whenever possible.

Every major subsystem owns:
- its lifecycle
- its update path
- its runtime data
- its configuration
- its teardown logic

Other systems communicate through:
- events
- readonly interfaces
- explicit contracts

2. COMPOSITION OVER INHERITANCE
-------------------------------------------------------------------------------
Do NOT build deep entity inheritance trees.

BAD:
Entity -> Enemy -> SpiderEnemy -> Warden -> EliteWarden

GOOD:
Warden
- MovementComponent
- AggroComponent
- LightPulseComponent
- StateMachineComponent
- LegAnimationComponent
- DamageComponent

3. NO GLOBAL MANAGER SPRAWL
-------------------------------------------------------------------------------
Avoid:
- EngineManager
- GameManager
- MegaController
- UniversalSingleton

Instead:
- narrow orchestration layers
- feature coordinators
- isolated systems

4. EVENT-ORIENTED COMMUNICATION
-------------------------------------------------------------------------------
Systems should NOT directly manipulate one another unless absolutely necessary.

Preferred:
EventBroker.emit(GameEvent.PLAYER_DAMAGED)

Avoid:
warden.damageSystem.player.health -= 1

5. DETERMINISTIC GAMEPLAY
-------------------------------------------------------------------------------
Core gameplay simulation runs fixed timestep.

Rendering may interpolate.
Gameplay may NOT.

This is critical for:
- rope behavior
- launch consistency
- collision predictability
- reproducible tuning

6. OBSERVABILITY FIRST
-------------------------------------------------------------------------------
Every major runtime system must expose:
- debug metrics
- runtime status
- profiling hooks
- validation helpers

The engine should be inspectable while running.

ABSOLUTE ARCHITECTURAL RULES
===============================================================================

RULE 1:
Gameplay systems NEVER directly touch React state.

RULE 2:
Babylon scene objects NEVER become source-of-truth gameplay state.

RULE 3:
React is presentation only.

RULE 4:
Physics owns authoritative movement truth.

RULE 5:
Visuals read gameplay state.
Gameplay never reads visuals.

RULE 6:
Every system has:
- init()
- update()
- dispose()

RULE 7:
No runtime circular dependencies.

RULE 8:
All cross-system communication must be explicit.

RULE 9:
Every feature module must be removable without catastrophic rewrites.

RULE 10:
No hidden side effects inside getters/setters.

===============================================================================
DEPENDENCY FLOW RULES
===============================================================================

Allowed:
UI -> Store
UI -> Readonly Gameplay State

Gameplay -> EventBroker
Gameplay -> Physics
Gameplay -> Rendering Adapters

Physics -> NONE

Rendering -> Readonly Gameplay

Forbidden:
UI -> Physics mutation
Rendering -> Gameplay mutation
Gameplay -> React hooks
Physics -> Babylon mesh ownership

===============================================================================
EVENT ARCHITECTURE
===============================================================================

Use a typed EventBroker.

NO raw string events.

Events are:
- immutable
- versionable
- explicit
- observable

Example:

GameEvent.PLAYER_LAUNCHED
GameEvent.TENSION_CHANGED
GameEvent.WARDEN_PHASE_CHANGED

Every event payload must:
- use readonly fields
- avoid passing mutable references
- avoid passing Babylon mesh refs directly

===============================================================================
STATE MANAGEMENT STRATEGY
===============================================================================

Zustand is NOT the simulation engine.

Zustand stores:
- HUD state
- debug state
- readonly snapshots
- menu-less overlay info
- reactive UI signals

Simulation state lives in systems.

DO NOT:
- put physics transforms in Zustand every frame
- use Zustand as ECS
- trigger React rerenders from simulation spam

Use snapshot throttling.

===============================================================================
GAME LOOP ARCHITECTURE
===============================================================================

REQUIRED:
Fixed timestep simulation.

Simulation:
60hz fixed

Rendering:
uncapped

Pipeline:
Input
-> Fixed Simulation
-> Physics
-> Gameplay Systems
-> Events
-> Render Sync
-> Babylon Render

Critical:
Clamp delta spikes after tab restores.

===============================================================================
ROPE SYSTEM DESIGN
===============================================================================

This is the heart of the game.

Architecture:
- rope simulation
- rope rendering
- rope gameplay evaluation

MUST be separate layers.

Simulation:
verlet or rapier joint chain

Rendering:
Babylon tube mesh

Gameplay:
tension
snap thresholds
launch impulse

DO NOT couple rope rendering directly to gameplay logic.

===============================================================================
ANCHOR SYSTEM
===============================================================================

Anchors are modular entities.

Each anchor owns:
- placement state
- durability
- tension contribution
- visuals

Future extensibility:
- sticky anchor
- elastic anchor
- temporary anchor
- explosive anchor

Architecture must support:
adding new anchor types WITHOUT modifying existing systems.

===============================================================================
SHADER ARCHITECTURE
===============================================================================

Shaders are isolated modules.

DO NOT inline giant shader strings inside TS files.

Use:
- dedicated .glsl files
- explicit uniform contracts
- shader adapter classes

Each shader gets:
- material wrapper
- parameter config
- debug controls

- tension

- phase escalation

Audio should be:
data-driven
event-driven

DO NOT:
scatter audio calls throughout gameplay code.

Use:
AudioEventRouter

===============================================================================
FAILURE CASE ANALYSIS
===============================================================================

1. Giant Monolithic Files
Risk:
Impossible onboarding and merge conflicts

Mitigation:
Feature modularization

2. Babylon Meshes Becoming Gameplay Truth
Risk:
Desync and nondeterminism

Mitigation:
Physics authoritative transforms

3. React Driving Simulation
Risk:
Frame instability

Mitigation:
Simulation isolated from UI

4. Event Spam
Risk:
Debugging nightmare

Mitigation:
Typed broker and diagnostics

5. Rope Instability
Risk:
Core mechanic collapse

Mitigation:
Fixed timestep and capped delta
